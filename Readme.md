## Установка

1. В корне приложения создаем конфигурационный файл Laravel:

```bash
cp .env.example .env
```

2. Разворачиваем контейнеры приложения через Docker compose:

```bash
docker-compose up --build -d
```

3. Одной командой устанавливаем зависимости, генерируем ключ Laravel, проводим миграции с сидерами:

```bash
make run
```

## Архитектурное решение:

Архитектурное решение - монолит с элементами SOA. Для простоты
разработки и развертывания проект реализован как монолитное приложение — весь код находится в одном репозитории и разворачивается как единое целое через Docker Compose. При этом сам код организован по принципу `Service-Oriented Architecture (SOA)`:
- `Сервисы:` основная бизнес-логика вынесена в отдельные сервисы
- `DTO:` четкая типизация данных между слоями
- `Job:` асинхронная обработка запроса (очереди)

В проекте использованы паттерны программирования Стратегия (`EmailChannel`, `TelegramChannel`), Фабричный метод (`ChannelFactory`), Dependency injection.

## Гарантия отправки уведомлений:

- При отправке уведомления с ошибкой сервис делает еще 2 попытки (время задержки между попытками 10 сек.). После третьей неудачной попытки статус уведомления меняется на `error`, а сама задача сохраняется в таблице `failed_jobs`
- Для генерации отчетов все то же самое, только статус после трейтьей неудачной попытки меняется на `failed`

В Horizon админитратор может отследить все упавшие задачи в разделе Failed Jobs, и вручную их перезапустить.

## Как улучшить в продакшене:

- Обязательно добавить JWT-авторизацию с Bearer токеном. Для ее осуществления можно воспользоваться пакетом Sanctum или Passport.
- Использовать Supervisor для автоматического поднятия контейнера с очередями, если он упадет.
  Можно добавить автоматический перезапуск (например, раз в полчаса) всех очередей из таблицы `failed_jobs`, чтобы не делать это вручную.
- Вместо Redis + Horizon можно использовать брокер сообщений RabbitMQ для более высокой и надежной гарантии доставки уведомлений.
- Добавить CI/CD для проверки Phpstan и pint перед каждым merge_request.

## Enums:

Каналы (channel):
- email
- telegram

Статусы уведомления (notification):
- pending
- sent
- error

Статусы отчета (report):
- pending - Ожидает генерации
- processing - Генерируется
- completed - Готов к скачиванию
- failed - Ошибка генерации

`GET` `api/v1/users/{userId}/notifications`

В параметрах запроса можно передать фильтры:

- channel - тип string,
- status - тип string,
- page - тип int

### Создать уведомление

`POST` `api/v1/notifications`

### Request:

```json
{
    "channel": "string", 
    "recipient_id": "int",
    "text": "string"
}
```

### Response:

```json
{
    "data": {
        "id": 91,
        "status": "pending"
    }
}
```

### Получить уведомление

`GET` `api/v1/notifications/{notificationId}`

Маршрут можно использовать для получения актуального статуса уведомления.

### Response:

```json
{
    "data": {
        "id": 91,
        "status": "sent"
    }
}
```

### Создать отчет

`POST` `api/v1/reports`

### Request:

```json
{
    "recipient_id": "int", 
    "from_date": "2026-07-01",
    "to_date": "2026-08-20"
}
```

### Response:

```json
{
    "data": {
        "id": 1,
        "status": "pending"
    }
}
```

### Получить отчет

`GET` `api/v1/reports/{reportId}`

Маршрут можно использовать для получения актуального статуса отчета

### Response:

```json
{
    "data": {
        "id": 1,
        "status": "completed"
    }
}
```

### Загрузить файл с отчетом

`GET` `api/v1/reports/{reportId}/download`

### Response:

Файл в формате .csv
